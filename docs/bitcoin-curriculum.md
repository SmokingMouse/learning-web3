# Section 0 · 为什么需要 BTC？

> **本章目标**：读者离开本章时，能回答三个问题——(1) 我们现在的货币系统到底依赖什么？(2) 这种依赖在什么情况下会出问题？(3) 去中心化数字货币真正难的是什么？（提示：不是"怎么转账"，而是"怎么达成共识"。）

### Page 0.1 · 直觉 — 一笔转账你看不见的中间过程
- 场景：你给朋友微信转 100 块。你看到的是"秒到"；实际发生了什么？
  - 微信 → 财付通 → 央行清算系统 → 对方银行 → 对方微信钱包
  - 每一步都在写一条账目：A 少 100 → 中间机构少 100（欠对方银行）→ 对方银行多 100 → B 多 100
  - 所有这些账本在**不同机构私有的数据库**里
- 跨境版本更离谱：SWIFT + 代理行 + 清算中心，可能 3-5 天到账，费用 $25-50，汇率加点 2-4%
- 关键观察：**"货币"本质是"在一堆相互信任的账本里记一笔"**
- 类比：这就像一群人相互欠人情，每人手里一个记账本，随时核对——只是"相互信任"这部分被法律、央行、监管替我们做好了。

### Page 0.2 · 推导 — 信任有成本，信任会失效
- 为什么需要中介？因为两个陌生人没有共同账本，需要一个"大家都信的第三方"来记账。
- 但中介有三个隐藏成本：
  - **费用**：Visa/Master 抽 1.5-3%，跨境转账 3-7%，拆家产时的律师费公证费
  - **延迟**：跨境 T+3，证券 T+2，银行关门不处理
  - **准入**：你得先开户、通过 KYC、国籍/信用符合要求
- 更深一层——信任本身会失效，而且是黑天鹅式失效：
  - **2008 雷曼**：美国第四大投行一夜破产，全球金融体系冻结
  - **2013 塞浦路斯**：政府为救银行强制没收储户 10% 存款 (Bail-in)
  - **2022 俄乌战争**：俄罗斯被踢出 SWIFT，海外 3000 亿美元资产被冻结
  - **2015 希腊**：每人每天 ATM 限取 €60，资本管制持续多年
  - **每年的委内瑞拉/阿根廷**：通胀率 50–500%，法币一年贬值一半
- 结论：**"信任第三方"在多数时候好用，但在极端情况下恰恰失灵**。BTC 是为"极端情况下也不失灵"设计的。

### Page 0.3 · 本质 — 现金 vs 数字，双花问题
- 现金为什么天然不需要账本？因为它是**物理独占**：你递一张 100 给对方，你手里就没了。物理世界的"守恒律"替你防了双花。
- 数字文件没有守恒律。一个 `.mp3` 文件复制一万份还是原文件。
- 这就引出核心难题——**双花 (Double Spending)**：
  - Alice 拿着一份"数字 100 块"，同时发给 Bob 和 Charlie。
  - 两人都看到"Alice 转我 100"，都认为自己收到了钱。
  - 没有中介裁决的话，谁都说不清哪笔有效。
- 关键结论（全书最重要的一句）：
  > **去中心化数字货币真正的难题，不是"怎么转账"，而是——在没有中介的前提下，让所有陌生人就"哪笔交易有效"达成一致**。
- 这是一个**共识问题**，不是一个**技术转账问题**。

### Page 0.4 · 对比 — 四种货币形态的本质差异
- 四象限对比（横轴：中心化程度；纵轴：物理/数字）：

  |        | 物理形态         | 数字形态            |
  |--------|----------------|--------------------|
  | 中心化 | 法币纸钞         | 银行存款 / 电子支付  |
  | 去中心化 | 黄金 / 贝壳     | **BTC**           |
- 每种形态的关键属性：
  - **法币纸钞**：物理独占、匿名、无手续费；但面对现金只能小额本地。
  - **银行存款**：可跨境可大额、可追溯；但依赖中介，可冻结、可印钞、有延迟。
  - **黄金**：稀缺、可验证、不依赖任何机构；但难分割、运输成本高、验真需要专业知识。
  - **BTC**：稀缺（2100 万封顶）、可验证、不依赖机构、可全球秒级转移、可分割到 10⁻⁸；但波动性大、私钥一旦丢失不可找回。
- **BTC 的真正"创新点"不是数字货币（之前 DigiCash、e-gold 早做过），而是"去中心化"——没有任何机构可以冻结、回滚、增发**。

### Page 0.5 · 历史 — BTC 不是一拍脑袋的产物
- 1990s：David Chaum 的 DigiCash，盲签名方案，但仍依赖中心化发行方，破产
- 1997：Adam Back 的 Hashcash，用计算工作量防垃圾邮件（PoW 雏形）
- 1998：Wei Dai 的 b-money，Nick Szabo 的 bit-gold，都是去中心化数字货币的设想但未落地——缺少共识机制
- 2008 年 10 月 31 日：Satoshi Nakamoto 发表 9 页白皮书 *Bitcoin: A Peer-to-Peer Electronic Cash System*
- 2009 年 1 月 3 日：创世区块诞生，附言: **"The Times 03/Jan/2009 Chancellor on brink of second bailout for banks"**（当天泰晤士报头条，讽刺银行救助）
- 白皮书的九位"巨人"（引用列表里致敬的人）大多是过去 20 年密码朋克运动的前辈。
- 核心启示：**BTC 是 30 年密码学、经济学、分布式系统的集大成，不是凭空冒出来的 idea**。

### → Bridge Question
- **已解决**：定位了核心难题——去中心化数字货币的本质是"就账本达成共识"，不是"怎么转账"。
- **遗留问题**：既然不要中介，那最直觉的想法是——**让所有人都持有同一份账本**。但这份账本怎么可信？

# Section 1 · 公开账本

> **本章目标**：理解"全网共享账本"这个方案为什么是对的方向，但它暴露出两个必须解决的硬伤——篡改 & 排序——引出后续两章。

### Page 1.1 · 直觉 — 雅浦岛的石头钱
- 太平洋雅浦岛的传统货币 Rai Stone：直径 1-4 米的石轮。
- 有的石头太重根本搬不动，甚至在运输中沉入海底。但岛民依然把它"花"来花去——靠什么？
- **靠集体记忆**：谁把哪块石头"给"了谁，全村人口口相传，人人知道每块石头的当前归属。
- 有一次一块石头运回岛的途中沉海了，但所有人都同意"它属于某某家族"，这块**看不见**的石头依然作为货币流通。
- 启示：**货币的本质不是"物"，而是"一份所有人都认同的账本"**。雅浦岛人用集体记忆维护账本；BTC 用密码学和算力维护账本。
- 这个故事告诉我们：公开账本不是新发明，只是 BTC 用数学把它做得更严密。

### Page 1.2 · 推导 — 公开账本必须具备的三个属性
- 既然没有中介，账本只能大家手里都有一份。每个节点收到广播的交易就追加到自己账本。
- 查余额？把某地址历史上所有收入减去所有支出即可。
- 但要让这份共享账本能运转起来，必须具备三个属性：
  1. **可追加**：任何人能广播新交易
  2. **不可篡改**：历史一旦写入，不能被偷偷改掉
  3. **顺序一致**：全网对"谁先谁后"的认知完全相同
- 第 1 点靠 P2P 广播解决（简单工程问题）。
- 第 2 点和第 3 点是 BTC 后续章节的主战场。
- 类比：Google Docs 是"可追加 + 中央服务器保证顺序一致 + 审计日志防篡改"。BTC 是"可追加 + 没有中央服务器 + 怎么办？"

### Page 1.3 · 硬伤 — 方案立刻暴露的两个致命问题
- **硬伤 1（完整性）**：账本是数据，数据就能改。
  - 恶意节点可以悄悄把"Alice 转 Bob 5"改成"Alice 转自己 5"
  - 发给新加入的节点一份伪造账本，新节点无从判断真伪
- **硬伤 2（共识/排序）**：Alice 几乎同时广播两笔互斥交易（花同一笔钱）
  - 北京的节点先收到"Alice → Bob"
  - 纽约的节点先收到"Alice → Charlie"
  - 两边各自把自己看到的那笔追加到账本——账本分叉
  - 没有裁判，谁都不肯让步
- 关键洞察：这两个硬伤本质都是**信任替代**问题
  - 以前信任银行替我们保证完整性和顺序
  - 现在没有银行，只能找"数学 + 博弈"替代

### Page 1.4 · 对比 — 银行账本 vs 公开账本
- 维度对比表：

  | 维度         | 银行账本               | BTC 公开账本              |
  |-------------|----------------------|--------------------------|
  | 可读        | 只有银行 + 本人        | 任何人                   |
  | 可写        | 只有银行               | 任何人（符合签名的）        |
  | 可验证      | 需要信任银行披露        | 每个节点都能独立验算全历史   |
  | 抗篡改      | 靠监管 + 法律 + 审计    | 靠哈希链 + PoW           |
  | 可用性      | 节日关门、跨境延迟      | 7×24 全球同步             |
- 权衡：
  - 公开账本的"隐私"反而不如银行（所有交易公开可见）——这是代价
  - 但"可审计性"碾压银行（任何人都能查，银行账本只有银行能查）

### Page 1.5 · BT 种子为什么不行？
- 很多初学者会问："账本不就是一个大文件吗？用 BitTorrent 互相传不就完了？"
- 这是一个重要的反思，因为它点出了金融账本和普通文件的本质差异：
  - **BT 种子**：分发的是**静态、已定稿**的文件。种子 hash 就是"这份文件"的身份，谁拿到的都应该一模一样。
  - **金融账本**：**动态、持续追加**。每秒都有新交易要进来，全网必须就"要不要接受、接在哪"达成一致。
- BT 解决的是"如何高效传输一份大家都同意的文件"；BTC 要解决的是"在没有中央裁判的情况下，如何就一份持续变化的文件达成一致"。
- P2P 只是 BTC 的**通信层**，真正的难题在**共识层**——下一章要攻克的。

### → Bridge Question
- **已解决**：确立了"公开账本"方向——不需要中介，让全网持有同一份账本。
- **遗留问题**：账本是数据，数据可以改。怎么让"改一个字就全网暴露"？

# Section 2 · 用哈希锁住账本

> **本章目标**：理解哈希函数的三个关键属性；理解"区块 → 链"的结构为什么能做到"改一处暴露一片"；但也要意识到——这还不够，攻击者可以重算后续所有哈希来掩盖篡改。这个缺口在下一章用 PoW 堵上。

### Page 2.1 · 直觉 — 摔碎的鸡蛋和不可逆
- 日常观察：鸡蛋很容易摔碎，碎了却几乎不可能拼回去。这是**单向过程**在物理世界的表现。
- 信息世界有对应的"单向过程"吗？有，就是**密码学哈希函数**。
- 哈希函数 $H$ 做的事：给任意数据 $x$ 算一个**短而固定长度**的"指纹" $H(x)$。
  - 从 $x$ 算 $H(x)$：瞬间
  - 从 $H(x)$ 反推 $x$：不可能
- 日常类比：
  - **指纹**：你的指纹能唯一识别你，但看到指纹没法"造"出你
  - **碎纸机**：一份文件粉碎后残渣长度固定但无法还原
  - **搅拌后的奶昔**：知道配料能调出固定的味道，但尝味道说不出具体配料比例

### Page 2.2 · 原理 — 哈希函数的三大属性
- **确定性 (Deterministic)**：同样的输入 **永远** 产生同样的输出。不受时间、地点、运行环境影响。
- **单向性 (Preimage resistance)**：给定 $h$，几乎不可能找到任何 $x$ 使得 $H(x) = h$。
- **雪崩效应 (Avalanche effect)**：输入改 1 位，输出大约一半的位会翻转。没有"相似输入 → 相似输出"这种事。
- 举例（SHA-256）：
  - `SHA256("hello")` = `2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824`
  - `SHA256("hellp")` = `b9a4b8dc93e09db5b6f9cc39b6b6d35e5d49f4d8aa55dc66fbf540b9bd91e96b`
  - 改一个字母（"o" → "p"），指纹完全不同
- 关键衍生性质：**抗碰撞 (Collision resistance)**——找到两个不同输入 $x_1 \ne x_2$ 但 $H(x_1) = H(x_2)$ 是不可能的。
  - SHA-256 输出 256 位 = $2^{256}$ 种可能
  - 暴力撞碰需要约 $2^{128}$ 次尝试（生日悖论）
  - 即使动用地球上所有计算机算到太阳熄灭，也撞不出来

### Page 2.3 · 构造 — 从"区块"到"链"
- **第一步：用哈希封装一个区块**
  - 一个"区块"就是一批交易的打包
  - 计算整个区块数据的哈希，附在区块上作为"身份证"
  - 任何交易被改动 → 哈希变 → 改动立刻可被发现
- **第二步：区块首尾相连成"链"**
  - 关键设计：每个新区块在自己的数据里，**把前一个区块的哈希**记下来
  - 这样一来：
    ```
    Block 1: hash=AAA, prevHash=genesis
    Block 2: hash=BBB, prevHash=AAA     ← 把 Block 1 的指纹记下
    Block 3: hash=CCC, prevHash=BBB     ← 把 Block 2 的指纹记下
    Block 4: hash=DDD, prevHash=CCC
    ```
  - 现在想改 Block 2 的一笔交易：
    - Block 2 的 hash 变成 BBB'
    - Block 3 里记的 prevHash 还是旧的 BBB，对不上 → Block 3 无效
    - 即使重算 Block 3，Block 4 又对不上……连锁崩塌
  - 所以改一个字 = 后面所有区块都得重算

### Page 2.4 · 历史 — 为什么是 SHA-256？
- 哈希函数不止一种。历史上有 MD5（已破）、SHA-1（已破）、SHA-2（当前工业标准）、SHA-3 等。
- 中本聪 2008 年选 SHA-256 的理由：
  - 2001 年 NIST 标准化，到 2008 年已被密码学界反复审查 7 年，无已知有效攻击
  - 256 位输出 → 抗碰撞至 128 位强度，安全裕度充足
  - 硬件实现简单高效（这点对 PoW 矿机很重要）
- BTC 实际使用的是 **SHA-256d** = `SHA256(SHA256(x))`（双重哈希）
  - 原因：防御长度扩展攻击 (Length Extension Attack)
  - 代价：2 倍计算成本，但对安全的投保很划算
  - 这是工程上的保守选择——密码学不是"越新越好"，而是"经过时间检验才可靠"

### Page 2.5 · 对比 — 防伪的物理 vs 数学
- 传统防伪（物理）：
  - 银行票据：水印 + 特殊纸张 + 金属丝 + UV 荧光
  - 奢侈品：全息标、防伪码、区块链+物流追溯
  - 特点：依赖"造假成本高于收益"——假钞机越贵，造假越难
- 数学防伪（哈希链）：
  - 伪造成本：重算从被改区块开始的**所有后续哈希**
  - 没有 PoW 的话，这个重算成本是 0（只需 CPU 几秒钟）
  - 所以哈希链**必须**和 PoW 结合才真正不可篡改
- 关键洞察：**哈希保证"改动立刻暴露"，但不保证"改动代价高昂"。后者是 PoW 的职责**。

### Page 2.6 · 局限 — 哈希链还解决不了的事
- 至此能做到：
  - 给定一份账本，任何人能验证"没人偷改过"（对比自己保存的哈希即可）
  - 区块之间形成连锁结构，局部改动牵动全局
- 仍解决不了：
  - 攻击者可以**重新计算**从某一点开始的所有哈希，伪造一份"内部自洽"的假账本
  - 如果计算哈希是廉价的（毫秒级），这种伪造几乎没有门槛
- 所以下一章要做的事：**让"算一个区块"变得非常昂贵**——昂贵到重算历史比造假收益还高。

### → Bridge Question
- **已解决**：用哈希链让账本变成"改一处暴露一片"的结构。
- **遗留问题**：但攻击者可以重算后续所有哈希来掩盖篡改。必须让"生成区块"本身变得昂贵。

# Section 3 · 工作量证明 (PoW)

> **本章目标**：理解 PoW 不是"浪费电"，而是"把抽象的共识问题转化成具体的物理成本问题"。理解最长链原则、51% 攻击的经济学、以及为什么"投票"不行。

### Page 3.1 · 直觉 — 为什么"证明你花了力气"很重要
- 现实生活里到处是"工作量证明"：
  - **大学文凭**：证明你花了 4 年时间 + 学费，过了考试
  - **健身身材**：证明你花了成百上千小时在健身房
  - **米其林餐厅**：证明主厨和团队经过长年训练、摆盘工艺复杂
- 这些证明的共同特点：**伪造需要付出和真实一样的代价**——这就是有效的凭证。
- BTC 版本：**"我生成了一个合法区块"这件事本身，必须证明我付出了真实的算力**。

### Page 3.2 · 机制 — 哈希前导零和 nonce 穷举
- 规则设计（简化）：**合法的区块哈希必须以若干个 0 开头**。
- 哈希是雪崩的——你不能"设计"一个前缀带 0 的哈希，只能试。
- 怎么试？区块数据里预留一个可随意修改的字段 `nonce`（一个 32 位整数）：
  ```
  区块数据 = {交易列表, 前一个区块哈希, 时间戳, nonce, ...}
  ```
- 矿工干的事：
  ```python
  while True:
      区块.nonce += 1
      h = SHA256(SHA256(区块))
      if h 以足够多个 0 开头:
          break  # 找到了！广播出去
  ```
- 没有捷径，只有不断试。难度 = 要求的前导零个数。每多 1 个前导零，期望尝试次数翻倍。

### Page 3.3 · 参数 — 为什么是 10 分钟一个块？
- BTC 的真实难度调整规则：
  - 每 **2016 个区块**（约 2 周）重新调整一次难度
  - 目标：维持**平均 10 分钟一个区块**
  - 算力翻倍 → 难度翻倍 → 出块时间回到 10 分钟
- 为什么选 10 分钟？工程折中：
  - **太快**（如 1 分钟）→ 两个矿工同时出块概率高 → 分叉频繁 → 全网同步不过来，共识不稳定
  - **太慢**（如 1 小时）→ 用户体验差，等太久才确认
  - 10 分钟让区块广播到全球大多数节点（一般几秒钟）的时间远小于出块间隔，分叉概率被压到最低
- 对比：
  - 以太坊选了 12 秒，用"最重子树 (GHOST)"算法处理频繁分叉
  - Litecoin 选了 2.5 分钟，Dogecoin 1 分钟，都是权衡结果

### Page 3.4 · 博弈 — 51% 攻击的经济学
- 表面上 PoW 的安全保证是数学的——"你没算力就没法伪造"。但真正的保证是**经济学**的。
- 假设攻击者想改一笔历史交易：
  - 必须从那笔交易所在区块**重算**后续所有区块
  - 同时全网诚实矿工还在源源不断地往前推进
  - 要追上并超过主链，需要**超过全网 50% 的算力**
  - 称为 "51% 攻击"
- 攻击成本（以 2024 年为例）：
  - 全网算力 ~500 EH/s，意味着攻击者需约 250 EH/s
  - 以顶级矿机 S19 XP (140 TH/s, $5000) 估算，需采购 ~180 万台 = 90 亿美元
  - 加电费、场地、运营——每天烧钱 ~3000 万美元
- 攻击收益：成功双花一笔几十 BTC 就要被主流交易所封禁，市场信心崩塌，BTC 价格暴跌 → **你手里所有矿机和 BTC 价值归零**
- 结论：**PoW 的安全不是"不可能被攻击"，而是"攻击比诚实挖矿更亏"**。这是精妙的激励相容。

### Page 3.5 · 分叉处理 — 最长链原则
- 即使 10 分钟的间隔，分叉还是会偶尔发生（两个矿工同时找到区块）。
- 协议规则：**每个节点永远跟随"累积工作量最大的链"**（实际实现上通常就是最长链）。
- 流程：
  1. 节点同时收到 A、B 两个合法区块，都先收在本地
  2. 下一个区块出来时（假设接在 A 后面），A 链长度 = 原 + 2，B 链 = 原 + 1
  3. 所有节点切换到 A 链，B 被"孤立"
  4. B 里的交易回到 mempool 等待下次打包
- 这也是"**6 次确认**"习俗的由来：
  - 你的交易所在块后又接了 6 块 → 攻击者需追上 7 块的差距
  - 在 BTC 算力分布下，被回滚的概率 < $10^{-18}$
  - 对高额交易，安全余量足够

### Page 3.6 · 历史 — 为什么"投票"行不通？女巫攻击
- 最朴素的共识方案：节点投票，多数派说了算。但有一个致命问题——
- **Sybil Attack（女巫攻击）**：网络上的"节点身份"是免费的
  - 我可以一人开一万台虚拟机，伪装成一万个节点
  - 一人投一万票，一人变成"多数派"
- 传统方案的"一人一票"建立在**身份可识别**的前提上（身份证、实名制、白名单）。去中心化系统里没有中央颁发的身份。
- PoW 的天才之处：**把投票权绑定在无法伪造的真实物理成本上**
  - "一份算力一票"
  - 你想多投票？去买电、买矿机、承担失败风险
  - 把抽象的"共识"问题转化成具体的"经济成本"问题
- 这是 1980s 以来分布式系统学界几十年都没解决的"拜占庭将军问题在开放网络下的实用方案"。中本聪用 PoW 给出了第一个可行答案。

### Page 3.7 · 对比 — PoW vs 传统共识机制
- 维度对比：

  | 机制           | 身份假设          | 抗攻击力来源       | 代表           |
  |---------------|------------------|-------------------|---------------|
  | 银行对账 (T+1) | 少数可信机构      | 法律 + 监管        | 央行清算       |
  | 拜占庭协议 (BFT)| 节点名单白名单    | 密码学 + 名单管理   | 联盟链、航空   |
  | Paxos/Raft    | 半可信多数        | 多数派投票         | Google 内部    |
  | **PoW**       | **开放，任何人加入** | **真实经济成本**   | **BTC**       |
  | PoS（权益证明）| 持币量决定权重    | 质押币经济成本      | 以太坊（2022）  |
- 关键区别：BTC 的共识不需要事先知道"参与者是谁"，这在所有传统方案里都做不到。
- 代价：能耗高、确认慢。

### Page 3.8 · 争议 — 能耗、ASIC、中心化
- **能耗**：BTC 网络年耗电 ~150 TWh，略多于阿根廷全国用电
  - 批评视角：为一个账本烧这么多电是否值得
  - 辩护视角：(1) 全球金融系统能耗更高（服务器 + 办公楼 + ATM + 运钞车）；(2) 越来越多矿场用弃水弃风电；(3) "能耗 = 安全预算"，你希望多少钱保护你 5000 亿美元市值的网络？
- **ASIC 集中化**：早期 CPU 挖矿 → GPU → FPGA → 今天的 ASIC 专用芯片
  - 问题：普通用户不能再挖矿，算力集中在少数矿场
  - 权衡：ASIC 矿工投入巨大、退出成本高 → 更有动机维护网络稳定
- **大型矿池**：前 3 名矿池控制 > 50% 算力
  - 表面看像单点风险，但矿池里的矿工可以随时切换
  - 历史上有过矿池接近 50% 时矿工主动撤离（2014 GHash.io 事件）

### → Bridge Question
- **已解决**：PoW 把"生成区块"变成昂贵行为，配合最长链原则解决了共识和防篡改——靠的是经济学不是数学。
- **遗留问题**：账本可信了。但账本上那行"Alice 转 Bob 5 块"——凭什么说这是 Alice 本人写的？

# Section 4 · 数字签名 & 地址

> **本章目标**：理解非对称加密如何解决"我是我"的身份证明；理解为什么 BTC 地址不是公钥而是公钥的哈希；明白"钱包"这个词的误导性——真正被保管的是私钥。

### Page 4.1 · 直觉 — 身份证明的演化
- 人类历史上的身份证明方式：
  - **印章**（中国、日本）：实物独占，但可被偷、可被仿
  - **签名**（西方）：笔迹特征，但笔迹可模仿
  - **人脸**：生物特征，但可用照片视频绕过
  - **指纹/虹膜**：更难伪造，但需要专用设备
  - **密码**：只有你知道，但易泄漏、被钓鱼
- 数字世界的挑战更严峻：没有物理空间的天然屏障
  - 有人发一句"Alice 转 Bob 100 BTC"到全网
  - 节点凭什么判断这真的是 Alice 发的？
- **数字签名**是密码学对这个问题的答案——**数学保证 + 任何人可验证**。

### Page 4.2 · 原理 — 非对称加密
- 每个人手握**一对**数学上关联的密钥：
  - **私钥 (Private key)**：一个随机大数（256 位），只有自己知道，严格保密
  - **公钥 (Public key)**：从私钥**单向**计算得出，可以公开给全世界
- 两个魔法操作：
  1. **签名 (Sign)**：用私钥 + 消息 → 生成一段"签名数据"
     ```
     signature = Sign(私钥, 消息)
     ```
  2. **验证 (Verify)**：用公钥 + 消息 + 签名 → 返回 True/False
     ```
     Verify(公钥, 消息, signature) → True/False
     ```
- 关键性质：
  - 只有知道**对应私钥**的人才能生成有效签名
  - 任何持有**公钥**的人都能验证签名
  - 消息被改一个字节，原签名立刻失效
- 类比：
  - 私钥 = 你家保险柜唯一的钥匙
  - 公钥 = 一个"照片已拍"的 QR 码，大家可以用它来核对保险柜的出品
  - 签名 = 保险柜里拿出来的盖着火漆印的信件

### Page 4.3 · 机制 — secp256k1 和 ECDSA
- BTC 用的是**椭圆曲线数字签名算法 (ECDSA)**，具体曲线是 `secp256k1`。
  - 曲线方程：$y^2 = x^3 + 7$（在有限域上）
- 为什么不用更耳熟能详的 RSA？
  - 同等安全下，ECC 密钥短得多：256 位 ECC ≈ 3072 位 RSA 的强度
  - 签名验证速度更快——BTC 每个节点要反复验证海量签名，性能关键
  - 硬件实现更紧凑，适合嵌入式设备（硬件钱包）
- 一次签名的流程（简化）：
  1. 对交易数据算 SHA-256 哈希 $h$
  2. 选一个临时随机数 $k$（**必须真随机，重复使用会泄漏私钥**）
  3. 结合 $k$、$h$、私钥做椭圆曲线运算，得到签名 $(r, s)$
  4. 广播时把签名和公钥一起附上
- 著名事故：2010 年 Sony PS3 因为签名时 $k$ 固定，黑客反推出 Sony 的签名私钥——整个游戏机破防。BTC 钱包对随机数质量有严苛要求。

### Page 4.4 · 地址 — 为什么不直接用公钥？
- BTC 地址长这样：
  - 传统（P2PKH）：`1A1zP1eP5QGefi2DMPTfTL5SLmv7DivfNa`
  - 新版（bech32/SegWit）：`bc1qxy2kgdygjrsqtzq2n0yrf2493p83kkfjhx0wlh`
- 地址不是公钥，是**公钥的哈希**（再加编码）：
  ```
  address = Base58Check( 0x00 || RIPEMD160( SHA256( publicKey ) ) )
  ```
- 这一圈弯路是故意的，有两个深意：
  - **更短更好抄**：公钥是 65 字节（未压缩）或 33 字节（压缩），地址 25 字节
  - **量子后备安全**：
    - 公钥一旦暴露，理论上量子计算机（未来）能反推私钥
    - 但地址只是公钥的哈希——量子对哈希无加速
    - 只要你每次都**用新地址**收款，旧地址的公钥永远不公开
    - 转账那一刻才暴露公钥——但那时币已经转出，无所损失
- Base58Check 编码的小心思：
  - 去掉易混淆字符：`0`、`O`、`I`、`l`
  - 带 4 字节校验码——手抄错一位，钱包立刻报错

### Page 4.5 · 地址形态演化
- P2PKH（`1` 开头）：Pay to Public Key Hash，最原始格式
- P2SH（`3` 开头）：Pay to Script Hash，支持多签等复杂脚本（2012 年引入）
- Bech32 / P2WPKH（`bc1q` 开头）：SegWit 引入（2017），更紧凑、纠错能力更强、大小写不敏感
- Bech32m / P2TR（`bc1p` 开头）：Taproot 引入（2021），支持更私密的多签和复杂合约
- 为什么有这么多？BTC 采用**软分叉**升级——新功能用新地址格式，老钱包不受影响。

### Page 4.6 · 对比 — 数字签名 vs 银行身份验证
- 维度对比：

  | 方式         | 身份凭证         | 防伪机制           | 失效场景              |
  |-------------|----------------|-------------------|----------------------|
  | 手写签名     | 笔迹            | 肉眼 + 鉴定专家     | 熟练造假者            |
  | 银行 U 盾    | 物理硬件 + PIN   | 内置私钥，用完销毁   | U 盾被盗 + PIN 泄漏   |
  | 人脸识别     | 面部生物特征     | AI 算法            | 照片、视频、3D 面具    |
  | 短信验证     | 手机号           | 运营商 + 用户持有   | SIM 交换攻击          |
  | **ECDSA**   | **256 位私钥**   | **数学不可伪造**    | **私钥泄漏**         |
- 关键差异：
  - 银行的身份验证**都需要银行作为验证方**——U 盾的签名只有银行能验
  - BTC 的签名**任何人用公钥都能验**——不需要中心化仲裁
  - 这是"无需信任第三方"在身份层的落地

### Page 4.7 · 陷阱 — "钱包"一词的误导性
- "钱包"这个词有很大的误导——它让人以为"钱在钱包里"。
- 真相：
  - **BTC 永远在链上**（更准确说：在 UTXO 集合里）
  - 钱包软件做的事是：保存**私钥** + 帮你签交易 + 查询你能解锁的 UTXO
  - 钱包本身**不存钱**
- 推论：
  - 私钥丢了 = 你的 BTC 永远锁在链上，没人能动（包括你自己）
  - 私钥被偷 = 对方可以立刻转走你所有的 BTC
  - 这就是那句名言：**Not your keys, not your coins**
    - 把币放交易所 = 交易所有私钥 = 你只是欠条持有者
    - 2014 Mt.Gox 破产、2022 FTX 暴雷都是活生生的教训
- 分类：
  - **热钱包**（联网）：方便、适合小额，易被攻击
  - **冷钱包**（离线）：安全、适合大额，易操作失误
  - **硬件钱包**（Ledger、Trezor）：私钥永远不离开设备，签名在设备内完成
  - **纸钱包**：私钥打印在纸上，绝对离线但易损坏

### → Bridge Question
- **已解决**：签名 + 地址 解决了"这笔交易是谁发的"——私钥即身份。
- **遗留问题**：账本上只有一笔笔"转账"，怎么快速算出"Alice 到底有多少钱"？

# Section 5 · UTXO：余额到底是什么？

> **本章目标**：理解 BTC 没有"账户余额"这个字段，只有一堆"硬币"；理解为什么选 UTXO 而不是账户模型，这是 BTC 和 ETH 最底层的世界观差异。

### Page 5.1 · 直觉 — 钱包里的硬币 vs 银行卡上的数字
- 想象两种"记账方式"：
  - **账户模型**：你有一张银行卡，卡里显示"23,456 元"。花 100 → 余额减 100。
  - **UTXO 模型**：你有一个真实钱包，里面装着"一张 100 + 一张 50 + 三个 1 元硬币"。花钱时要挑出具体的钞票，不够还得掏更多再找零。
- BTC 用的是后者。
- 为什么？因为"账户余额"这个抽象，在没有中央裁判的情况下**极难维护一致性**。
- 而"每一枚硬币能不能花"是一个**二值判断**——要么已花（spent），要么未花（unspent）——简单到不可能出错。

### Page 5.2 · 机制 — UTXO 的一笔交易是什么样
- UTXO = **U**nspent **T**ransaction **O**utput（未花费的交易输出）
- 一个 UTXO 包含：
  - 金额（比如 0.5 BTC）
  - 锁定脚本（谁能花它——通常是"某地址持有者"）
  - 它是哪一笔过去交易的第几个输出（作为"身份证"）
- 一笔交易的结构：
  ```
  交易 = {
    inputs:  [UTXO_A, UTXO_B, ...]     // 要消耗哪些 UTXO
    outputs: [新UTXO_1, 新UTXO_2, ...] // 生成哪些新 UTXO
    signatures: [...]                  // 证明我有权花 inputs
  }
  ```
- 约束：
  - 输入总额 ≥ 输出总额
  - 差额 = 矿工手续费
  - 每个输入 UTXO 必须提供合法解锁脚本（签名）
- 生命周期：
  - 一个 UTXO 从"被创建"到"被花"之间叫 unspent
  - 被花掉的瞬间 → 从 UTXO 集合中移除，永不可用
  - BTC 网络维护的"状态"就是全体未花 UTXO 的集合

### Page 5.3 · 实例 — Alice 转 Bob 7 BTC 的完整过程
- Alice 钱包里有：4 张 UTXO = 3, 5, 2, 10 BTC，总计 20 BTC
- Bob 的地址：`1Bob...`
- Alice 要转 Bob 7 BTC。步骤：
  1. **选币 (Coin Selection)**：挑出总和 ≥ 7 的组合，比如 5 + 3 = 8 BTC
     - 钱包软件用算法挑（FIFO、最小找零、隐私最佳……）
  2. **构造交易**：
     ```
     inputs:  [ UTXO_5, UTXO_3 ]     # 总计 8 BTC
     outputs: [
       {金额: 7 BTC,    给: Bob 的地址},
       {金额: 0.9 BTC, 给: Alice 的找零地址}   # 回到自己
     ]
     # 手续费 = 8 - 7 - 0.9 = 0.1 BTC
     ```
  3. **签名**：用对应私钥签 inputs
  4. **广播**：传播到全网
  5. **打包**：某矿工把它打进新区块
  6. **生效**：
     - UTXO_5 和 UTXO_3 从全局状态中移除（花掉了）
     - 两个新 UTXO（7 给 Bob + 0.9 给 Alice）进入状态
- 现在 Alice 钱包：10, 2, 0.9（找零）共 12.9 BTC
- Bob 钱包多了 7 BTC UTXO

### Page 5.4 · 为什么选 UTXO（vs 账户模型）
- **并行验证友好**
  - 不同交易如果用的是不同 UTXO，**完全并行**验证
  - 账户模型下，同一账户的两笔交易必须排队（余额是竞争资源）
- **天然抗双花**
  - 共识层只需一个问题："这个 UTXO 是否已被花？"——一个布尔判断
  - 账户模型要问："余额够不够"+"nonce 是否重放"——多一层状态
- **无状态验证更容易**
  - 只需保存"全体 UTXO"，不需要全链历史
  - 适合裁剪 (pruning)——节点可以丢弃很久以前的区块
- **隐私（潜在）更好**
  - 同一个人可以用无数地址收款，UTXO 独立
  - 账户模型下地址即身份，所有交易都聚合在一个账户下
- **代价**：
  - 钱包管理 UTXO 集合更复杂
  - 交易大小略大（需列出输入输出）
  - 用户体验上没有"余额"字段——只能扫链加总

### Page 5.5 · Bitcoin Script — UTXO 怎么"锁"
- 每个 UTXO 带一段**锁定脚本**（locking script / scriptPubKey）
  - 最常见 P2PKH 脚本：
    ```
    OP_DUP OP_HASH160 <收款人公钥哈希> OP_EQUALVERIFY OP_CHECKSIG
    ```
    翻译：给我一个签名，且公钥哈希 = 指定值
- 花这个 UTXO 时要提供**解锁脚本**（unlocking script / scriptSig）
  - 内容：`<签名> <公钥>`
- 节点执行拼接后的脚本，栈顶为 true = 合法花费
- **Bitcoin Script 故意不图灵完备**：
  - 只有几十个操作码
  - **没有循环**（while, for）
  - **没有递归**
  - 设计目的：简单 + 可预测 + 不可能被恶意脚本拖垮网络
- 这是和 Ethereum Solidity 的根本差异：ETH 要支持任意合约，牺牲了简单性换来表达力；BTC 保持极简，换来可审计和稳定。

### Page 5.6 · 对比 — UTXO (BTC) vs Account (ETH / 银行)
- 维度对比：

  | 维度          | BTC (UTXO)              | ETH / 银行 (Account)       |
  |-------------|------------------------|---------------------------|
  | 状态单位     | 一个个独立 UTXO           | 账户余额字段               |
  | 查余额       | 扫链加总 unspent 的       | 读一个字段                 |
  | 花钱         | 消耗输入，生成输出         | 余额加减                   |
  | 双花检查     | "这 UTXO 花过了吗"         | "余额够+nonce 对吗"         |
  | 并发友好性   | 极好（UTXO 独立）         | 差（同账户要排队）           |
  | 智能合约     | 极有限（Script 不图灵完备） | 强大（EVM）                |
  | 心智模型     | "硬币"                   | "账户"                    |
- 深层差异：
  - UTXO 把钱当**不可变的硬币**，只有"花掉"和"未花"两态
  - Account 把钱当**账户里可加减的数字**
  - 上层所有体验（gas 模型、并发特性、合约形态、隐私特性）差异都源于这个根本选择
- 哲学对应：
  - UTXO 像**函数式编程**（不可变、可并行、无副作用）
  - Account 像**命令式编程**（可变状态、顺序依赖）

### Page 5.7 · 实战 — UTXO 的隐私陷阱
- 听起来"多地址 = 隐私好"，但实际上……
- **找零地址揭示所有权**：
  - Alice 输入 5+3 BTC，输出 7 给 Bob + 0.9 找零给自己
  - 链分析者会推理："0.9 的金额更像找零" → 这个地址也是 Alice 的
  - 两笔交易被关联
- 链分析公司（Chainalysis、Elliptic）就靠这类启发式规则追踪资金流
- 对抗手段：
  - **CoinJoin**：多人交易混合，打乱输入输出的关联
  - **Taproot**（2021）：让多签和单签看起来一样
  - **Lightning Network**：链下交易，只有开关通道时上链
- 启示：BTC "伪匿名"（地址不是实名），但**不是完全匿名**——链上一切可追溯。隐私要用专门手段构建。

### → Bridge Question
- **已解决**：UTXO 模型说清了"余额是什么"——它是你能解锁的硬币集合。
- **遗留问题**：一个区块有几千笔交易。手机钱包不想下载 1GB 才能确认自己那笔被打包了。怎么办？

# Section 6 · Merkle Tree：轻客户端的魔法

> **本章目标**：理解 Merkle Tree 是如何用"根哈希 + O(log n) 哈希"证明单笔交易存在于区块中的；理解这个数据结构在 Git、IPFS、ZK Rollup 里都是同一个灵魂——"用一个小指纹承诺一大堆数据"。

### Page 6.1 · 动机 — 手机钱包的两难
- 一个 BTC 区块大约 ~2MB（SegWit 后可至 4MB 等效），包含几千笔交易。
- 全链至今 ~500GB 并每年增长 ~50GB。
- 手机钱包的困境：
  - 想：一键安装、立刻收发 BTC、独立验证交易
  - 做不到：下载 500GB 全链
- 需要一个折中方案——**轻客户端** (SPV = Simplified Payment Verification)
  - 只下载区块头（每个 80 字节），累计 ~60 MB
  - 但如何证明"我那笔 Alice → Bob 的交易确实在 #810000 区块里"？
- 简单方案：把整个区块发给我 → 违背 SPV 初衷
- 聪明方案：**Merkle Proof**——只发给我"证明路径"的几个哈希

### Page 6.2 · 构造 — 二叉哈希树
- 把区块里所有交易作为"叶子"，两两配对做哈希：
  ```
            [ Merkle Root ]              ← 写进区块头
              /       \
          H_AB       H_CD
          /  \       /  \
        H_A  H_B   H_C  H_D               ← 叶子层
         ↑    ↑    ↑    ↑
         Tx_A Tx_B Tx_C Tx_D               ← 实际交易
  ```
- 计算过程：
  - `H_A = SHA256(SHA256(Tx_A))`
  - `H_AB = SHA256(SHA256(H_A || H_B))`
  - `H_CD = SHA256(SHA256(H_C || H_D))`
  - `Root = SHA256(SHA256(H_AB || H_CD))`
- 性质：
  - 任何交易变 → 它的哈希变 → 它到根的路径全变 → Root 变
  - 反过来：Root 没变 → 所有交易一个没动
- 这个 Root 就**承诺**了区块里所有交易

### Page 6.3 · 魔法 — Merkle Proof
- 现在手机钱包的老板要验证：`Tx_C` 是否在这个区块里？
- 全节点给手机钱包发三样东西：
  1. `Tx_C` 本身（让钱包自己算 `H_C`）
  2. `H_D`（`Tx_C` 在树里的"兄弟"）
  3. `H_AB`（上一层的"兄弟"）
- 钱包自己算：
  - `H_C = SHA256(SHA256(Tx_C))`
  - `H_CD = SHA256(SHA256(H_C || H_D))`
  - `Root' = SHA256(SHA256(H_AB || H_CD))`
- 和区块头里的 Root 一比——相等 → 证明 `Tx_C` 确实在里面
- 数据量：
  - 树高 $= \log_2 n$
  - 一笔证明只需 $\log_2 n$ 个兄弟哈希
  - 4000 笔交易（$\log_2 4000 \approx 12$）→ 12 个哈希 = 384 字节
  - **对比**：全量下载需要 2MB，差 5000 倍

### Page 6.4 · 为什么是二叉树？
- 二叉是"验证路径最短"和"实现最简单"的平衡：
  - 三叉树：验证要给 2 个兄弟，路径略短但成本更高
  - 四叉树：3 个兄弟，边际收益递减
- 叶子数不是 2 的幂时 BTC 的做法：**复制最后一个叶子补齐**
  - 这个实现曾导致漏洞 CVE-2012-2459：
    - 同样 merkle root 可对应两个不同树结构
    - 可以制造"看起来有效但实际是 DoS" 的区块
  - 后续通过拒绝"重复交易"修复
- 启示：**密码学原语安全，工程实现会出坑**。Merkle 本身没问题，是 padding 规则的边界条件没想清楚。

### Page 6.5 · Merkle Tree 的广泛应用
- **Git**：一个 commit = 一个树哈希 + 父 commit 哈希 + 元数据
  - 每个目录是一个 tree 对象，每个文件是一个 blob
  - `git diff` 本质是比较两个 Merkle 树
  - 这就是 Git 能快速判断"哪些文件变了"的原因
- **IPFS**：内容寻址 (Content Addressing)
  - 文件的地址就是它的 Merkle 根
  - 同样内容无论存在哪里，地址都一样
  - 天然去重 + 抗篡改
- **ZK-Rollup**：Layer 2 的状态用 Merkle 树表示
  - 只把 Root 上链，证明用零知识证明压缩
- **证书透明度 (Certificate Transparency)**：Google 用 Merkle Tree 记录所有签发的 HTTPS 证书
  - 任何浏览器都能验证"这个证书真的被登记过"
  - 事后发现问题也能追溯
- **数据库**：一些分布式数据库用 Merkle Tree 做节点间状态同步（Dynamo、Cassandra）
- 共同灵魂：**用一个小的根哈希 承诺 一大堆数据，并能高效证明"某一项在其中"**

### Page 6.6 · 对比 — 传统金融的"证明"
- 传统世界里，"我的交易被记录了" 怎么证明？
  - **银行交易单据**：你保留回单，银行保留副本——依赖银行承认
  - **对账单**：银行每月发 → 你比对——还是依赖银行披露
  - **审计**：第三方每年查一次——年度级时间分辨率
- 共同特点：**证明依赖银行配合**。银行可以不给、可以迟给、可以造假（真实的安然事件）。
- Merkle Proof 的革命性：
  - **自验证**：拿到 proof 后完全独立验证，不需要任何人配合
  - **秒级**：1 秒内能验 O(log n) 个哈希
  - **不可伪造**：假 proof → root 算不对 → 被识破
- 这是"**用数学替代信任**"在数据结构层的实现。

### → Bridge Question
- **已解决**：Merkle Tree 让 SPV 钱包用 O(log n) 数据量验证交易被打包——轻客户端的理论基础。
- **遗留问题**：账本、共识、签名、余额、验证全都有了。最后一个问题：挖矿奖励的 BTC 从哪儿来？第一个 BTC 凭什么凭空出现？

# Section 7 · Coinbase & 减半：2100 万的来源

> **本章目标**：理解第一个 BTC 是怎么凭空生成的（Coinbase 特殊交易）；理解 2100 万不是中本聪拍脑袋拍的，而是"50 BTC 起始 + 每 21 万块减半"这两个参数的数学必然结果；理解为什么选减半曲线而不是匀速减少。

### Page 7.1 · 裂缝 — 第一个 BTC 是哪来的？
- 前面讲 PoW 时说过："矿工找到有效区块 → 获得 BTC 奖励"
- 但这句话有个裂缝——如果所有 BTC 都来自"之前的交易"，那**第一个 BTC** 从哪来？
- 答案：每个区块的**第一笔交易**是一种特殊交易——**Coinbase 交易**
- Coinbase 交易的特殊之处：
  - **没有输入**：不从任何 UTXO 里转出
  - **只有输出**：凭空生成一笔 BTC 给矿工
  - 协议里硬编码了"这种无输入的交易合法"这条规则
- 翻译：**协议授权矿工"凭空印一笔钱"给自己**，作为为网络提供算力的奖励。
- 类比：
  - 像央行印钞，但"印多少"由**确定算法**规定，不是央行行长临时决定
  - 像美联储，但 FOMC 会议决策被换成了数学公式

### Page 7.2 · 奖励 — 不是永恒不变
- 初始奖励（2009 年 1 月）：每块 50 BTC
- 每 **210,000 个区块**（约 4 年）减半一次
- 到目前为止的历史：

  | 阶段          | 区块范围            | 每块奖励   | 起始日期       |
  |--------------|--------------------|-----------|---------------|
  | 创世          | 0 — 209,999         | 50 BTC    | 2009-01-03    |
  | 第 1 次减半   | 210,000 — 419,999   | 25 BTC    | 2012-11-28    |
  | 第 2 次减半   | 420,000 — 629,999   | 12.5 BTC  | 2016-07-09    |
  | 第 3 次减半   | 630,000 — 839,999   | 6.25 BTC  | 2020-05-11    |
  | **第 4 次减半** | 840,000 — 1,049,999 | 3.125 BTC | **2024-04-20** |
  | 第 5 次减半（预）| 1,050,000 —         | 1.5625 BTC | 2028          |
  | ...          | ...                | ...       | ...           |
- 到大约 2140 年，奖励趋于 0（精确说：奖励在 32 次减半后归零）

### Page 7.3 · 数学 — 2100 万的来源
- 把每个阶段的总产出加起来：
  ```
  总量 = 210,000 × 50 + 210,000 × 25 + 210,000 × 12.5 + ...
       = 210,000 × 50 × (1 + 1/2 + 1/4 + 1/8 + ...)
  ```
- 关键观察：括号里是**几何级数**
  $$\sum_{k=0}^{\infty} \frac{1}{2^k} = 2$$
- 所以：
  ```
  总量 = 210,000 × 50 × 2
       = 21,000,000 BTC
  ```
- **"2100 万"不是中本聪拍脑袋的整数**——它是"每块 50 BTC + 每 21 万块减半"这两个参数的**数学必然结果**。
- 反过来：如果一开始选 40 BTC 和 21 万，总量就是 1680 万。选择"恰好 2100 万"是回过头算出来的——中本聪很可能先定总量，再反推起始奖励。
- 小趣闻：实际上最终总量略小于 2100 万（约 20,999,999.97），因为早期整数运算的取整损失。这是一个工程实现细节。

### Page 7.4 · 经济学 — 减半 vs 匀速减少
- 为什么选**减半**这种"跳变"曲线，而不是**线性**或**指数连续衰减**？
- 减半的三个好处：
  - **可预期稀缺性**：下一次减半在哪个区块是**精确已知**的（甚至可以秒级预测时间）
    - 2024 年 4 月 19 日 UTC 精确到小时全球都在直播
    - 没有哪个法币能做到"14 年前就知道 2024 年 4 月某一天通胀率腰斩"
  - **市场叙事简单**：每 4 年一次关注度高峰
    - 减半前供应收紧 → 历史上都伴随牛市（2013、2017、2021）
    - 虽然历史不保证未来，但"数字黄金"叙事因减半节奏变得清晰
  - **工程实现简单**：一个 if 判断即可。连续衰减要浮点运算，不同实现可能出数值分歧
- 经济学关键指标 **Stock-to-Flow (S2F)**：
  - S2F = 当前总存量 / 年新增产出
  - 黄金 S2F ≈ 60（地面黄金 / 年采矿量）
  - BTC 每次减半，S2F 翻倍
  - 2024 年减半后，BTC S2F > 黄金
  - 有经济学家认为这是 BTC 长期价值的数学基础（PlanB 的 S2F 模型，争议颇大）

### Page 7.5 · 创世区块的"附言"
- Coinbase 交易的输入字段可以放任意数据（因为没有实际输入意义）。
- 2009 年 1 月 3 日，中本聪在创世区块的 Coinbase 里写下了那句名言：
  ```
  The Times 03/Jan/2009 Chancellor on brink of second bailout for banks
  ```
- 这是当天伦敦《泰晤士报》的头版标题，意思是"英国财政大臣考虑对银行进行第二次救助"。
- 双重意义：
  1. **时间戳证据**：证明创世区块**不早于** 2009 年 1 月 3 日
  2. **意识形态宣言**：把 BTC 诞生钉在 2008 金融危机的历史坐标上——银行系统需要政府救助，而 BTC 是另一条路
- 后来的矿工也延续这个传统，在 Coinbase 里放各种数据（广告、政治宣言、个人寄语）。

### Page 7.6 · 未来 — 2140 年后矿工吃什么？
- 区块奖励最终趋于 0。那时矿工靠什么维持算力？
- 答案：**交易手续费**
  - 每笔交易 inputs 总额 - outputs 总额 = 手续费
  - 归打包该交易的矿工所有
  - 用户愿意付多少费用 = 这笔交易的优先级
- 现状：
  - 2024 年区块奖励占矿工收入 ~95%，手续费占 ~5%
  - 预期：随减半推进，手续费占比逐渐上升
- 关键争议（长期经济学）：
  - **激进派**：BTC 作为"世界结算层"，每笔交易费会变高（大额、高价值）
  - **保守派**：如果交易需求不够，手续费养不起算力 → 安全性下降
  - **折中派**：Lightning Network 等 Layer 2 消化小额，主链只做结算
- 这是 BTC 长期存续问题中最核心的经济学辩论，至今没有定论。

### Page 7.7 · 对比 — 三种"货币供给控制"
- 对比法币、黄金、BTC 的发行机制：

  | 货币  | 供应控制方     | 供应上限   | 发行节奏                  | 透明度          |
  |------|--------------|-----------|-------------------------|----------------|
  | 法币  | 央行 + 财政部  | 无        | 由货币政策决定             | 间接（公报）    |
  | 黄金  | 地质 + 矿企    | 理论有限   | 自然禀赋 + 技术进步         | 供应报告        |
  | BTC  | **算法**      | **2100 万** | **精确公式可预测到 2140** | **全链可查**    |
- BTC 的独特性：
  - **供应上限明确**：2100 万，写在代码里
  - **节奏可预测**：每一分钟的产出量都能算到 10 年后
  - **无人可改**：修改需要全网共识（实际不可能）
- 这不是"数字黄金"的比喻——这是**可编程的稀缺性**，人类货币史的新形态。

### → Bridge Question
- **已解决**：Coinbase + 减半 把"BTC 从哪来"讲清楚了——协议规则凭空生成，节奏可预测，总量封顶 2100 万。
- **遗留问题**：所有零件都到位了。最后一节把它们串起来，走一遍一笔交易从出生到被确认的完整旅程。

# Section 8 · 完整旅程：一笔交易的一生

> **本章目标**：把前 0–7 节的所有零件组装起来，跟随 Alice 给 Bob 转 1 BTC 的这笔交易，走完从出生到 6 次确认的全过程，每一步对应前面哪一节的知识。

### Page 8.1 · 剧情设定
- Alice 要给 Bob 转 1 BTC
- Alice 钱包里有两个 UTXO：0.6 和 0.7 BTC
- 网络当前平均手续费率：10 sat/vB
- 一笔普通交易大约 250 vB，所以手续费约 2500 sat = 0.000025 BTC

### Page 8.2 · Step 1 — Alice 钱包构造交易
- 钱包软件干的活：
  1. **选币**：挑 0.6 + 0.7 = 1.3 BTC 作为输入（← 第 5 章 UTXO）
  2. **算找零**：1.3 - 1 - 0.000025 = 0.299975 BTC 找零给自己
  3. **组装交易**：
     ```
     inputs:  [UTXO(0.6), UTXO(0.7)]
     outputs: [
       {1 BTC       → Bob 地址},
       {0.299975 BTC → Alice 找零地址}
     ]
     ```
  4. **签名**：用 Alice 私钥对交易哈希做 ECDSA 签名（← 第 4 章）
  5. 把签名放进解锁脚本 scriptSig

### Page 8.3 · Step 2 — 广播到网络
- Alice 钱包连上任一 BTC 节点，发送交易
- 节点检查（验证合法性）：
  - 输入 UTXO 确实未花 ✓
  - 签名有效 ✓（← 第 4 章）
  - 输入 ≥ 输出 ✓
  - 脚本合规 ✓
- 通过后：
  - 放进 **mempool**（待打包交易池）
  - 转发给它的邻居节点
  - 消息以病毒式 gossip 传遍全网（几秒到十几秒）
- 此时：交易"看得见"但**未被确认**

### Page 8.4 · Step 3 — 矿工打包
- 全球矿工都在用自己的 mempool 打包候选区块（← 第 3 章 PoW）
  - 策略：优先打包手续费率高的交易
  - Alice 的 10 sat/vB 是平均水平，会被打包但不是最优先
- 某矿池 M 把 Alice 的交易放进自己的候选区块：
  - 连带前几千笔其他交易
  - 第一笔是 Coinbase，奖励 3.125 BTC + 所有手续费 → 矿池地址（← 第 7 章）
  - 把所有交易哈希做 Merkle Tree → 得 Merkle Root（← 第 6 章）
  - 区块头 = {版本, prevHash, Merkle Root, 时间戳, 难度目标, nonce}
- 矿工开始穷举 nonce，直到 `SHA256(SHA256(blockHeader))` 小于难度目标
  - 平均 $\sim 10^{22}$ 次尝试才撞到一个
  - 10 分钟左右会出一个

### Page 8.5 · Step 4 — 找到有效区块，广播
- 某瞬间，矿池 M 的一台矿机找到了合适的 nonce
  - 立刻组装好完整区块
  - 广播给它的邻居节点
- 其他节点收到后：
  - 验证区块头哈希确实满足难度 ✓
  - 验证每笔交易 ✓
  - 验证 Merkle Root ✓（← 第 6 章）
  - 验证 prevHash 接的是当前最长链 ✓（← 第 2 章 + 第 3 章）
- 所有检查通过 → 把区块追加到本地链 → 转发给邻居
- 15-30 秒内，全球大多数节点都已收到并接受此区块
- 此时 Alice 的交易 = **1 次确认**

### Page 8.6 · Step 5 — 等待更多确认
- 随后 10 分钟左右，下一个区块出来
- 无论是哪个矿工出的，只要接在刚才那个块后面 → Alice 的交易 = **2 次确认**
- 以此类推：
  - 10-20 分钟：2 次确认（小额支付一般够了）
  - 30-60 分钟：3-6 次确认（交易所入金）
  - 60+ 分钟：6+ 次确认（大额结算标准）
- 每多一次确认，攻击者要回滚就得超过对应数量的算力——成本指数级上升（← 第 3 章经济学）
- 约定俗成的 "6 次确认" 标准：回滚概率 < $10^{-18}$

### Page 8.7 · Step 6 — Bob 收到了
- Bob 的钱包监听区块 → 发现自己地址下多了一个 UTXO（1 BTC）
- Bob 余额 +1 BTC
- Alice 那 0.6 + 0.7 两个 UTXO 被标记为 spent，Alice 的"余额"现在包含新找零 0.299975 BTC
- 交易完成

### Page 8.8 · 全流程对照表
- 一笔交易走过的零件：

  | 步骤                    | 涉及章节                  |
  |-----------------------|--------------------------|
  | Alice 钱包存私钥、算公钥地址 | Section 4（签名 & 地址）    |
  | 选 UTXO 作为输入          | Section 5（UTXO）         |
  | 签名证明持有私钥            | Section 4                |
  | 广播到 P2P 网络            | Section 1（公开账本）       |
  | 矿工打包进区块              | Section 3（PoW）+ 7（奖励）|
  | Merkle Tree 计算 root    | Section 6                |
  | 穷举 nonce 找有效哈希      | Section 3                |
  | 区块接入哈希链              | Section 2（哈希链）        |
  | 全网对最长链达成共识         | Section 3                |
  | SPV 钱包用 proof 验证交易 | Section 6                |
- 看到了吗——**每一个零件都在这条路径上登场，并且缺一不可**。删掉哪一个，整个系统都会在某一环倒塌。

### Page 8.9 · 终极视角 — 这一切为了什么？
- 回到 Section 0 的那句话：
  > 在没有中介的前提下，让所有陌生人就"哪笔交易有效"达成一致
- 我们现在看明白了：
  - **公开账本** 提供"大家都在记同一本账"的框架
  - **哈希链** 让账本历史改不动
  - **PoW** 让记账权需要真实成本
  - **签名** 让"是我发的"可被验证
  - **UTXO** 让"能不能花"是简单的布尔判断
  - **Merkle Tree** 让轻客户端也能验证
  - **Coinbase + 减半** 解决了"钱从哪来"和"供应可控"
- **BTC 的每一个零件都是被前一个问题逼出来的解**——不是灵感，是推导。
- 学完这 9 节，你不只懂 BTC，你懂了**去中心化系统如何用密码学 + 博弈论替代传统信任**。
- 这个思想会重新塑造你对货币、身份、数据所有权、甚至治理结构的理解。
